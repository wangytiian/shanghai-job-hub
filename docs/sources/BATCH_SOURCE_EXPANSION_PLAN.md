# 招聘抓取源批量扩充方案

日期：2026-09-06。交付范围：方案文档，不执行抓取接入、不修改业务代码。

## 1. 推荐决策

一次建立 12 个候选渠道的验证队列，按适配难度和学生内容价值排序，争取首轮启用 3–5 个有效来源。3–5 是工作目标，不是已验证承诺；遇到简单且合格的来源可继续启用，不限每周一家。

默认沿用当前上海学生求职定位，覆盖应届、实习、金融、国企、专业服务及技术岗位。全国校招公告只有明确包含上海工作地点或上海岗位附件时才进入上海推荐；上海高校发布不代表岗位在上海。

用户希望“盲增加一批”，本方案将其落实为批量筛选和技术试跑：先扩候选覆盖，再根据结果开启自动采集。无需逐家请求用户确认，只有付费采购、账号授权或扩大地域范围才提出业务问题。

## 2. 什么算接口

- 官方文档 API：有公开文档和调用规则；本轮未核实到此类新增招聘 API。
- 页面使用的公开 JSON 接口：例如 NCSS 已发现的列表请求；不等于承诺长期兼容的开放 API。
- 公开 HTML 栏目：能读取招聘列表和详情，也可做抓取源，无须强求 JSON。
- 只有首页、登录页或动态外壳：只是候选入口，尚不是可工作的抓取接口。

下表是入口调查与实施优先级，不表示 12 个渠道都能立即自动抓取。优先级为基于定位和本次可见内容的判断，实际难度由列表和详情试跑决定。

## 4. 执行批次与时间投入

### 第一批：高优先级 4 个来源

华东理工、交大、上财、NCSS。先调查，再做适配。每站首轮技术调查投入上限约 45 分钟；有明确进展可继续，否则记录障碍并切换下一站。该上限是工程排期，不是网络超时。

每站先取 1 个列表、最多 3 篇详情；列表无记录或访问失败时换一个同站公开栏目核实，不反复刷新相同空页。NCSS 必须按 sourcesNameCh 分组取样，并比较已有完整详情样本，不能仅凭前三页判定全平台不可用。

### 第二批：4 个高校渠道

华师大、上大、上理、上经贸。核实是否与第一批采用相同页面结构。只有实际结构一致才复用解析器；域名相似、栏目名称相似不构成复用依据。

### 第三批：4 个复杂或低频渠道

上海公共就业、中信、德勤、上海国际集团。判断登录、动态数据和招聘季限制。公开页面可稳定采集则接入；需要账号时输出明确需求，暂不扩大授权。

建议安排为 3 个实施批次，整体约 5–8 个工程工作日作为初始排期假设。每批结束报告实际时间和产出，再调整后续投入。动态站点可能超出估算。

## 5. 必须补齐的共用能力

扩源前或与首批一起完成以下针对现有实现的修正，避免把缺陷复制到新适配器：

1. 地点读取岗位字段或正文的明确工作地点段落，不能因整页出现“上海”而判断为上海岗位。
2. “投递简历”必须属于该岗位有效申请控件或可信状态字段；隐藏弹窗、通用提示不算证据。没有申请按钮的官方公告可按公告日期、截止日期和招聘正文判断，不能一刀切排除。
3. 连接成功、详情解析成功、有效新增分别统计。30 条详情全部失败不能记录为采集成功；确认空列表应表达为空，不能自动算故障。
4. 岗位身份使用来源命名空间与稳定岗位 ID/规范 URL，发布时间和企业显示名称变化不生成新身份。跨来源重复保留来源关系，不简单删除其中一条。
5. 已有岗位下线时更新生命周期、使旧审核与草稿失效；未在前三页出现不等于下线。为已有有效岗位安排有界详情复核，超出预算则记录上次验证时间。
6. 保存来源单位、平台详情、企业原始公告链接与采集时间。高校发布和公共平台收录都不等于企业原文已核实。

这些是对已确认数据质量要求的落实，无需改变 FastAPI、SQLAlchemy、worker 或 PostgreSQL 架构。

## 6. 数据流和工作台呈现

候选来源 → 小样本验证 → 合格来源定时采集 → 内容检查与去重 → 待核验 → 现有审核发布流程。

保留原 A/B/C/D 分类。新增候选先登记 B 类禁用；已有 C/D 来源不批量改级。每个来源另行表达“HTML/JSON/人工链接”和“未测/列表可读/详情可读/验收通过/受限”，不要把采集方式塞入字母等级。

正文不足的列表条目只进入试采报告或独立候选样本记录，本期不为此新建人工线索产品模块、不混入 Job，不把它算有效岗位。

## 7. 每个来源的启用标准

- 正式栏目有官方入口依据，真实列表和详情可公开读取，采集路径遵循站点公开使用条件。
- 至少 3 个不同详情样本正文完整；至少 1 个具有当前可用、学生相关和上海地点证据。其他样本可用历史公告测试，但不计有效新增。
- 相同样本在隔离数据库运行两次不重复新增；明确区分实时页面更新与去重异常。
- 更新正文使旧审核失效，下线阻断旧稿，相关离线测试通过。
- 在两个不同时间点复测，并记录时间；不承诺一次 HTTP 200 即代表长期稳定。
- 不要求每个招聘公告都有明确截止日期；缺日期保留缺口，发布前人工核验，不能把采集日期伪装为发布时间。
- 通过小样本验收后仍保持 B 类禁用，完成连续 3 次正式试采成功、正文清洗合格并经人工确认后，才可升 A 类；保持运营人员已有的暂停/禁用决定，初始化不得悄悄恢复。

## 8. 请求预算与观察指标

初始每源每日最多 1 轮，3 页列表、30 个新详情，单站并发 1、全局并发最多 3，单请求 12 秒、请求间隔至少 0.5 秒。已有岗位复核预算每源每日另外最多 10 条；失败后不立即无限重试。遵循站点更严格的限流要求。

网络出口校验重定向目的地址、限制重定向次数和响应大小；不能关闭证书验证或绕过登录/验证码。禁止在日志保存 Cookie、请求凭据及投递表单内容。标准 httpx 超时是操作超时，不要将它描述成严格整轮总时限。

每轮输出：请求列表数、发现岗位数、成功详情数、正文不足数、下线数、非上海数、学生匹配数、重复数、新增待核验数、人工采纳数。解析失败与业务过滤分别计数。

首轮验收目标是完成 12 个渠道的可复核分类与首批合格接入；3–5 个新增自动源是期望值。如果不足，明确逐源原因与替代顺序，不能靠空解析器或降低质量门槛达标。

观察 7 天后按“独有且被人工采纳的招聘内容 / 维护投入”排序。已有岗位覆盖高但新增少的来源可作核验来源，降低采集频率，无须删除。

## 9. 实施交付物

1. 候选清单：来源 ID、官方依据、列表入口、详情样本、类型、优先级、状态、阻碍、最后验证时间。
2. 每站适配器及脱敏离线样本；相同结构的公共解析器要有跨站样本证明。
3. 隔离试采命令与报告，默认不写正式岗位库。
4. 修正来源状态、稳定身份、下线更新和原始来源保留的相关测试。
5. 启用清单与来源页实际状态；正式采集仍进入待核验，不自动对外发送。
6. 运行受影响测试；批次完成后运行完整测试，有数据库变化才新增迁移并验证 PostgreSQL。报告真实通过和跳过原因。

建议文档放在 docs/sources/，适配器放 app/sources/，分发沿用 app/services/real_collection.py。确需新字段先写字段映射和迁移，再编码；不添加 LangChain、浏览器集群或独立抓取服务。

## 10. 实施提示词

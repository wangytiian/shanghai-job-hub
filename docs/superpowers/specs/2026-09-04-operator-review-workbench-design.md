# 运营审核工作台优化设计

## 目标

把当前的真实招聘线索列表变成一个可日常使用的运营工作台：运营人员能清楚分辨入库初筛、AI 建议与人工最终结论；能批量处理建议分；并在进入待审核前完成一组可追溯的人工核验。

本期不改公众号视觉模板、不自动发布、不改变来源抓取策略。

## 已确认的边界

- `A/B/C/D` 是入库初筛等级，不是发布结论。
- `AI 建议分` 只决定处理优先级，不修改岗位状态，不替代人工最终质量分。
- `最终质量分` 仍只由人工填写，且发布规则继续要求不低于 70 分。
- 没有统一截止日期不是阻断条件；审核人员须确认公告仍有效，并在发布稿中明确“以官方原文为准”。
- 批量建议分只处理真实、待核验、可投的新招聘；已截止、招聘进度通知、D 级和已有人工作最终分的记录不得进入。

## 方案比较与选择

### 方案一：在现有列表增加说明文字

改动最小，但运营人员仍要逐条进入详情理解建议状态；不解决批量处理、规则兜底和优先顺序问题。

### 方案二：列表顶部增加轻量运营队列（本期采用）

在现有岗位中心顶部增加一张“今日 AI 建议队列”，显示待建议、AI 已生成、规则兜底、无需建议四个数量，并提供批量入口与结果反馈。列表同时增加建议状态筛选和排序。

优点是保持当前数据库和审核流程，学习成本低；缺点是不做后台异步任务，单批仍受 5 条上限约束。

### 方案三：独立后台任务中心

可展示逐条进度、耗时和失败重试，但需要新增任务状态、轮询和更复杂的运维机制。本期没有必要先引入。

## 数据和交互设计

### 1. 岗位中心

新增明确的文案层级：

- `入库初筛`：A 优先待核验、B 普通待核验、C 人工复核、D 过滤留档。
- `AI 建议分`：显示分数与 `AI建议 / 规则建议 / 待建议 / 不适用`。
- `人工最终分`：显示“未确认”或人工填写的最终分。

默认排序为：真实线索优先、待核验优先、A/B/C 顺序、AI 建议分从高到低、最新拉取在前。新增“建议状态”筛选，不改变已有的属性、初筛、状态和关键词筛选。

顶部队列只在存在符合条件记录时显示。点击批量生成后，按钮进入加载态，完成后返回同一列表并显示：本批处理数、AI 建议数、规则建议数、跳过数。不会重复处理已建议岗位。

### 2. 人工审核清单

公告结构化页在最终质量分前展示六项必核项：

1. 原始来源已核对；
2. 岗位或公告范围已确认；
3. 面向学生人群已确认；
4. 工作地点已确认；
5. 官方投递入口已核对；
6. 时效已确认，或原文未明确统一截止日期但公告仍有效。

六项以复选框保存为审核事实。未全部确认时，提交后停留在当前页面，缺失项标红并说明原因；不会跳到原始 JSON 错误页。人工最终分输入保留为空，只有完成核验清单并填写 0–100 的分数后才能提交到待审核。

AI 建议分区显示简短理由、置信度和评分构成，并明确“只作参考”。对于规则建议，明确显示“模型未形成可核验建议，已保留规则基础分”，避免被误认为低质量岗位。

### 3. 发布准入

现有的发布校验继续生效，并在此基础上加入审核清单校验。截止日期为空不会失败；系统只要求记录审核人员选择“时效已确认”。

### 4. 操作反馈

- 所有批处理按钮禁用并显示处理中，防止重复点击。
- 成功反馈留在原页面，包含结果统计和“下一步”链接。
- 失败反馈显示简短、可行动的原因，不暴露 JSON 或模型响应原文。
- 单条字段校验使用字段下红字，而不是跳转错误页。

## 测试与验收

- 岗位中心能按 AI 建议状态筛选，且把 A/B/C 真实待核验岗位排在前面。
- 批量按钮仅处理符合条件的岗位；第二次点击不会重复调用已经有建议的记录。
- 无截止日期的岗位只要勾选时效确认即可提交；其他缺失核验项会在当前表单标红。
- 提交后的审核记录包含六项人工核验状态。
- 任何 AI 建议分都不会覆盖 `quality_score`，也不会自动变更为可发布。
- 现有全量 pytest 继续通过。

## 非目标

- 不在本期改造微信公众号文章视觉模板。
- 不接入公众号或个人微信自动发送。
- 不将 AI 当作事实来源或自动审核人。
